# Prodcraft 流程效率、可读性与协作审计

日期：2026-10-02。首次检查依据当时工作区，HEAD 为 `fd05978`。同日提交核对确认：远端 `main` 的 `d81156c` 所含 1,406 个文件与工作区逐字节一致；这些源码修订已经入库，旧本地索引造成了大量表面脏状态。

本文是面向维护者的非规范性中文审计与改造建议（non-authoritative），不修改[现行仓库规则](../../../CLAUDE.md)，不表示方案已经实施或批准。审计范围是用户已经说明的三项问题；空白的第 4 项不作推断。

## 结论

三个问题存在共同根因：仓库对“流程记录是否完整、协议是否一致”的约束，比对“某一步是否值得执行、上游结果是否减少了下游工作”的验证更充分。已有系统化设计，但尚不能证明这些设计带来的质量收益抵消了使用与维护成本。

当前最值得做的是收敛既有入口和协作契约，保留有效的专业能力，以完整任务的结果验证改进。只缩短文本、翻译标题，或新增一层调度系统，都不足以解决全部问题。

证据支持入口负担、语言边界与用户期望不一致、协作收益未闭环这些判断；本轮没有测量真实返工率，不能宣称已量化全部损失，也不能承诺消灭返工。

- 机械检查覆盖 46 个源码 Skill、40 个分发包；分发包包含生成的入口，不是另有 40 项独立能力。
- 重点阅读入口、问题澄清、需求、系统设计、任务拆分、实现交接、工作流、产物契约、分发生成器和相关测试。

## 流程繁琐：轻量化原则尚未贯穿实际入口

[入口 Skill](../../../skills/00-discovery/pc-intake/SKILL.md)允许零问题、复用已有授权，也提供 `micro`。这些设计值得保留。但同一文件要求 `micro` 仍输出全部 schema 必填字段，并明确当前 Claude Edit/Write adapter 拒绝 `micro`。

[入口 schema](../../../schemas/artifacts/intake-brief.schema.json)有 18 个基础必填字段，另有嵌套的质量上下文和按模式增加的约束。因此“小任务走轻量路线”目前主要缩短说明和审批方式，没有真正把记录成本降到与任务相称。不能把可选严格执行协议的全部成本归给所有任务；它在[入口规则](../../../skills/_gateway.md)中仍明确为可选。

本轮静态测量为：

- 仓库脚本定义的入口文件集合：36,922 字符。
- 其中 gateway：17,161 字符；intake 主文件：12,177 字符。
- 46 个源码 Skill 的描述合计：9,903 字符；正文合计：162,676 字符。

这些是文件清单测量，包含按需参考资料，不表示每次任务都会全部加载，也不是实际 token 或耗时。

改造重点应是减少强制判断与重复记录：低风险工作只保留足以指导执行和验收的信息；当风险、范围或授权发生实质变化时再增加相应检查。高风险行动仍需明确权限和证据。已有批准、需求和验证结果应在适用时直接消费。

## 可读性：展示规则与权威产物采用了不同语言政策

[CLAUDE.md](../../../CLAUDE.md)、[gateway](../../../skills/_gateway.md)及[入口 I/O 契约](../../../skills/00-discovery/pc-intake/references/io-contract.md)已经要求根据实质请求选择语言，覆盖标题、状态标签和完成说明。因此不能诊断为“完全没有自动语言规则”。

与此同时，intake、problem-frame、requirements-doc 的 schema 把 `artifact_record_language` 固定为 `en`；[语言契约测试](../../../tests/test_language_boundary_contract.py)明确断言中文记录语言无效。这样即使回复是中文，供用户审计的权威内容仍被要求保留英文，用户需要在摘要与原始记录之间切换。schema 只检查语言字段，不检测正文实际语言。

[展示指引测试](../../../tests/test_user_facing_guidance.py)主要验证规则文本存在，并没有执行中文或英文任务来检查最终标题。因此现有测试通过，仍不能证明用户得到正确语言的完整产物。

建议明确三个边界：

1. Skill 源码、字段名、枚举、路径、API 名称可以继续采用稳定英文标识。
2. 面向用户的标题、决策理由、问题描述、验收内容与报告正文，随当前请求语言变化；不能只翻译聊天摘要。
3. 切换展示语言不应重新触发入口审批或改变已有授权；修改产物语言契约时要兼容历史英文记录，并同步 schema、模板、生成器和测试。

## 编号：追踪价值与阅读价值没有充分分开

[路线模板](../../../templates/route-decision.md)和[验证模板](../../../templates/verification-record.md)直接展示 `work_id`、`route_id`、证据 ID 和摘要等协议字段。[需求 Skill](../../../skills/01-specification/pc-requirements-engineering/SKILL.md)也要求每条需求携带 ID。这些标识有追踪用途，但标识本身不说明问题是什么、结论是什么。

没有证据表明协议强制使用随机 UUID；例如 [route-decision schema](../../../schemas/artifacts/route-decision.schema.json)允许有含义的英文短名。因此不应将所有编号一概认定为无意义，也不宜直接删除稳定标识、摘要或内容绑定。

建议使用有业务含义的标题作为主阅读入口，例如“访客不得导出成员名单”；需要跨文档追踪时再附稳定编号。机器标识、完整摘要与版本绑定保留在元数据或详细证据中。主报告先回答“为什么做、决定了什么、依据是什么、还缺什么”，用户无需来回查编号才能理解结论。小任务不要求为每个段落再生成一个编号。

## 系统协作：已有结构与契约，消费质量仍主要依赖执行者

仓库已具备生命周期、工作流、产物生产与消费关系，不能说它只是平铺的 Skill 列表。[gateway](../../../skills/_gateway.md)也明确要求最短充分路线、复用有效产物、按需加载和按问题组织评审；[Skill 编写约定](../../../skills/_schema.md)已经区分必需、条件性和可选输入。

关键缺口在于这些约定如何被验证：

- [artifact-flow 校验](../../../scripts/validate_prodcraft.py)核对生产者、消费者和引用关系，不判定下游是否真正使用了上游结论。
- [工作流契约](../../../tools/workflow_contract.py)能检查字段、阶段和 Skill 引用，不证明组合后的任务更快、缺陷更少。
- [已有设计记录](../../architecture/2026-09-08-skill-execution-design.md)明确承认，按需加载、产物复用和组合仍是 agent 执行的指引，不是已经验证有效的自动执行机制。

不必因此立即增加调度器。更小的第一步是把既有职责收敛为三个协作层，并用真实交接场景检验：

| 协作层 | 应负责的判断 | 对应现有位置 |
|---|---|---|
| 总控入口 | 目标、范围、风险、现有授权、下一项未满足的要求 | gateway、intake、入口生成器 |
| 工作流模块 | 当前任务需要哪些专业结果、顺序和条件；何时可以继续 | workflows、phase 说明、已有任务记录 |
| 专业 Skill | 解决一个专业问题，消费已有结果，交付下游可直接使用的内容 | 各 Skill 主文件及 I/O 契约 |

这三个层级首先是职责划分，不意味着新增三个目录、三套状态或新 Skill。

交接应沿用已有任务记录或产物中的相关章节，只传递目标与约束、已确认决策、证据指针、未解决项和下游验收条件。一个事实保持一个权威来源；大任务可以保留分开的专业文档，由任务记录引用，不把所有内容合并成巨型文件。

上游变化时，只使依赖该变化的结论和检查失效。需求未变就不重做需求；同一发现由不同评审角度引用，不重复登记；并行只用于确实独立、收益超过协调成本的工作。不同角色名称不能把同一次自审变成独立审核。

## 质量与效率：需要评价完整任务的净收益

[现有行为评测交接](../../../eval/meta/2026-09-08-skill-design-handoff.md)已经提出比较“不用 Skill、简短通用清单、Prodcraft”。首次审计遗漏了后续[9 月 11 日验收记录](../2026-09-11-strict-host-closure.md)，此处更正：仓库已有一次同模型、同任务、每组一次的原生小任务对照，三组均通过相同的五项测试；修复回合分别耗时 57.268、44.356、98.768 秒，严格流程三次原生调用合计 181.725 秒，尚不包含人工复核时间。该记录未观察到实现质量优势，观察到额外执行与审核成本；它不是统计充分的效率基准，也不能代表普通非严格路线。

同一记录还包含六个真实语言样本及两次受限替代探针；其中后续语言切换采用重构上下文，并非真正续会话测试。不能说语言行为完全没有验证，也不能由这些样本推出所有产物、标题和续会话都可靠。

因此下一轮应复用这个历史试验的方法与局限，新增当前候选、普通路线、跨模块交接和实际返工的验证，而不是重复宣称需要从零建立全部证据。当前 manifest 为 33 个 `review`、13 个 `tested`、0 个 `production`；这些状态不等价于全部能力不可用，也不能证明系统整体达到用户期望。

前道质量应以减少下游错误为目的。开始实现前，重点解决成功标准、关键约束、接口边界和代价高的未知数；低风险、可逆且不会改变方案的细节可以在实现中完善。不能把“尽量避免返工”变成“编码前填写全部文档”。

评测应复用已有基础设施，优先选取三类完整任务：局部修复、跨模块功能、带真实风险或发布要求的变更。让不同方案面对相同任务和独立验收标准，分别记录：

- **交付质量**：真实需求与边界是否通过验收、遗留或漏检了什么缺陷。
- **返工**：首次下游消费后，因上游遗漏或错误而重做的工作；主动改变需求与必要探索另行记录。
- **整体成本**：从请求到被验收的总耗时、人工等待、审批轮数、上下文和工具使用；缺失测量保持未知。
- **交接质量**：下游是否能直接继续，有无重复提问、重新推导或抄写同一事实。
- **可读性**：读者能否从主报告直接找到目标、决定、证据和剩余问题，无需解码编号。

质量与成本分别列出，不压成容易掩盖权衡的单一分数。先得到基线，再制定有依据的改进阈值；没有真实运行数据时，不报告节省比例。

## 改造选择与建议顺序

| 选择 | 作用与代价 | 判断 |
|---|---|---|
| 只精简文案、翻译标题 | 变更小，能改善阅读；入口记录和协作验证问题仍在 | 可做局部修复，不能作为全部问题的解决方案 |
| 收敛现有入口、交接与展示契约，并用完整任务对照验收 | 能沿用专业能力和验证基础；需要同步规则、契约与测试 | 推荐 |
| 重建调度器或工作流平台 | 可能自动化部分状态处理，但会增加运行、迁移和维护成本 | 当前证据不足以支持优先投入 |

建议先锁定三类任务的当前基线与验收标准，再分批推进：

1. **统一人能读懂的输出**：任务标题、报告正文和状态随请求语言变化；机器标识保留可追踪性。验证中文、英文、混合提示词与后续语言切换。
2. **压缩日常入口成本**：让低风险入口真正变轻，同时保证源码、schema、模板和宿主执行路径一致。保留风险变化与外部操作所需的授权。
3. **收敛交接责任**：在既有 I/O 契约里写清消费结果、失效条件和下一步，不再添加一套平行流程。验证有效输入复用、依赖变更、重复评审和局部返工。
4. **同任务比较并决定去留**：验证质量不被削弱且总成本改善；无收益的步骤继续合并或删除。行为证据充分后才考虑状态晋级或全局部署。

这些是本次审计的行动建议，不是用户空白第 4 点的代填。每一批应可独立回退；涉及 schema 的改动必须考虑历史记录兼容，不能通过删除既有验证来获得表面通过。
