# Skill 执行设计修订——非规范性中文导读

日期：2026-09-08；最近实现修订：2026-09-09。

本文是[英文设计记录](2026-09-08-skill-execution-design.md)的中文说明，包含同一轮自我复盘。它不定义或修改任何项目规则；如与英文记录、`CLAUDE.md`、schemas、validators、workflow contracts 或 distribution registries 有冲突，以英文规范来源为准。

## 本轮决定

围绕“需要做什么判断、交付什么可被下游使用的结果”改进现有 Skill 系统。保留生命周期、产物契约、工作流组合和可选的严格执行授权机制。本轮没有新增 Skill、调度器、产物类型或依赖。

交付重点是单个 Skill 的设计，以及 Skill 之间如何配合。完整行为评测另行交接。[原仓库审计](../reviews/bs-skill-auditor/2026-09-08-health-report.md)仍是 `fd05978dbbbf5a064205a695af47c8a550f1b224` 的历史快照。

## 系统层面的变化

| 要解决的判断 | 当前规则 | 预期作用 |
|---|---|---|
| 继续执行，还是重新进入 intake | 目标、范围和授权未变时继续；新工作或实质变化才重新判断路线 | 减少重复 intake 和重复审批 |
| 下一步使用哪个 Skill | 从尚未满足的要求出发，为当前判断或交付选择一个主要 Skill，保留必需的 gate | 避免默认执行整个生命周期 |
| 是否重做上游工作 | 先检查现有产物的范围、有效性、质量和审批；满足输入契约则引用并消费 | 让交接真正使用已有结果 |
| 需要读取哪些上下文 | 先读当前 Skill 与必需的 I/O 契约；到具体步骤时再读方法和相应 gotcha | 避免预先读入全部工作流和引用 |
| 多个评审如何分工 | 分别回答意图、代码缺陷、实现真实性和完成证据问题；允许在一份报告中保留独立章节 | 减少重复检查和重复报告 |
| 什么时候需要再做一轮 | 下一轮必须解决明确缺口；相同阻塞没有新证据时，先补事实或回到相关上游环节 | 避免为了得到“通过”而反复改写 |
| 公开包是否遵守相同入口规则 | 将 Core Rule 纳入生成的 portable routing map，并更新共享 gateway renderer | 使源码与公开包的入口指引一致 |

这些是设计和执行指引，不会自动控制模型读取什么，也不会自动产生执行权限。严格执行模式下的 obligation、状态转换和 operator pin 含义没有改变。把同一次自审换成几个 persona 名称，不能变成独立审批。

## 单个 Skill 的变化

| Skill | 设计改进 |
|---|---|
| `pc-intake` | 恢复新 bug、review 的入口判断；复用已有授权；允许一个 Skill 的路线和零问题；用示例说明主流程与 overlay 如何组合 |
| `pc-system-design` | 从已有架构或进程内方案出发；新增边界必须有真实需求支撑；按实际运行环境决定图和部署说明的深度 |
| `pc-task-breakdown` | 按可观察结果和真实依赖拆任务；时长作为规模参考；权衡并行带来的收益和协调成本 |
| `pc-task-execution` | 只有批次划分能解决实际问题时才使用；复用上游计划；阻塞发生时暂停依赖它的步骤，并继续独立且已授权的工作 |
| `pc-tdd` | 区分新增行为和既有行为的 characterization；保留已有代码；诚实记录基线失败；Skill 文本与视觉工作采用适合的检查 |
| `pc-code-review` | 阻塞项必须有具体缺陷或明确项目规则作为依据；按根因合并发现；仓库专用 scanner 及例外语法只在适用时使用 |
| `pc-implementation-alignment-review` | 复用需求覆盖关系；未经授权的延期不能被算作完成；只检查与声明相关的产物 |
| `pc-implementation-integrity-audit` | 聚焦隐藏失败和证据替代；区分“没有足够证明”和“已经证实存在伪装” |
| `pc-verification-before-completion` | 对同一声明复用仍有效的证据；变更影响哪些检查就重跑哪些；区分设计交接完成和行为已就绪 |
| `pc-delivery-completion` | 执行已经授权的结果；分别处理 commit、push、PR、merge 和 deployment 的权限 |

Skill 编写说明补充了“进入、消费输入、做判断、产出、继续或停止”的设计约定。工作流说明解释了产物复用、overlay、交接内容和评审来源；没有改变 `workflow.v2` 字段。

## 适用条件与权限边界

- 现有产物必须满足输入质量要求；文件名相同或文件存在都不够。
- 共用报告必须保留各项必需结论及评审来源，不能绕过 schema 或严格证据绑定。
- 路线变化、外部操作和缺失的权限仍需对应审批。记录一笔技术债不能代替 blocking gate 的授权。
- 当前 Claude Edit/Write adapter 不接受 `micro`。9 月 8 日仅明确这一限制；9 月 9 日已修复 FIFO 和 draft intake 恢复，详见下方实现修订。
- 公开包不会因为被调用，就自动安装仓库 hook 或替换使用者的 Git 配置。

最初一轮修改 10 个 Skill，后续设计轮次增加 6 个，全库验收再增加 14 个，当前共 30 个 `review` 候选。最初 10 个 Skill 的状态变化为：3 个保持原状态，4 个从 `production` 回到 `review`，3 个从 `tested` 回到 `review`。此前的成熟度和证据保留为历史记录；当前记录说明的是设计评审和待完成的行为评测。现有公开包继续作为允许列表中的 beta 候选，相关 `core` 标记改为 `beta`。

[行为评测 handoff](../../eval/meta/2026-09-08-skill-design-handoff.md)记录了候选契约、包摘要、后续场景、预期判断和实际运行过的检查。刷新摘要不是完成模型评测，也不是获得成熟度晋级。生成仓库内公开包不等于已经全局安装或发布。

如需回退，可从审计基线恢复本轮涉及的源码契约、gateway renderer/projection 和状态记录，再重新生成 `.curated/`。应保留无关的用户改动与历史审计。本轮没有修改主机配置或全局安装的 Skill。

## 自我复盘

### 判断

**方向合理，但目前是范围明确的候选设计修订，还不能叫作“系统优化已经完成”。** 最有价值的变化，是将不分场景的流程改成有条件、有依据的判断，同时保留产物要求和审批边界。主要不足是：这些改进多数仍靠 agent 阅读并执行。renderer 和 routing projection 负责把规则交给使用者，并没有实现自动引用加载、产物复用或调度。

### 已有实现能支持的结论

- 架构和任务拆解更接近实际目标：新增组件、图和批次包装都需要解释其必要性。
- Intake 与交付区分了已有授权和新增授权：请求 review 不会顺带授权合并，分支规则也不能自动授权 push 或创建 PR。
- 评审各自回答不同问题，可以复用已有发现，但不能伪造独立评审。
- TDD 仍默认先写测试并观察失败；characterization 可以先通过。若过早写了实现，需要隔离自己的改动、补充基线证据并如实记录，不能把这条补救路径当成正常工作流。停止信号列表也受同样的适用条件约束。
- 当前 `review-report.v1` 能容纳分章节的报告，但 schema 兼容不代表 agent 已被证明能正确执行这种分工。

### 做得不够的地方

1. **读者文档没有一起完成。** 第一轮只改英文 README，遗漏了中文导读，连英文状态日期也没有更新。本次已补齐两种 README 和中文设计记录。
2. **最初的语义检查没有覆盖全部引用。** 独立评审陆续发现 C4、时长、输入要求、hotfix 顺序和授权分支中的残留冲突；本次自审又发现 delivery gotcha 会直接把结果转换成 PR。具体冲突已经修正，但不能因此声称 46 个 Skill 的全部规则都经过深度评审。
3. **静态上下文没有整体缩减。** Description 略短，但入口栈和正文总量增加了。“按需加载”是希望 agent 做出的行为，尚不是测量结果。
4. **执行机制仍有欠账。** 9 月 8 日快照中，引用内容证据绑定和 Claude adapter 的 FIFO/draft 修复尚未完成；9 月 9 日已补上这些实现。这不只是缺测试，确实有实现工作未收口。
5. **结果质量仍不能下定论。** 分支更清楚，不等于架构决策必然更好、漏掉的缺陷更少或协作成本更低。当前检查主要证明打包和契约一致性。

| 静态源码指标 | 审计基线 | 当前修订 | 变化 |
|---|---:|---:|---:|
| 全部 authored descriptions | 10,330 字符 | 10,183 字符 | -147 |
| 入口栈 | 36,720 字符 | 37,978 字符 | +1,258 |
| 全部 authored Skill 正文 | 160,785 字符 | 164,452 字符 | +3,667 |

以上采用仓库 context meter 的文件范围，并对 `fd05978dbbbf5a064205a695af47c8a550f1b224` 使用相同口径计算。它们不是运行时 token 计费，也不覆盖全部引用依赖。通过预算上限检查，不能被表述为本轮降低了上下文成本。

### 下一步真正有价值的工作

保持本轮候选的 `review` 状态，将已知执行机制缺陷作为独立实现批次完成。设计方面，检查三条完整的上游到下游使用过程：继续已批准的任务、brownfield 变更、发布决策。每个产物都应回答下游的实际问题，每个新增步骤都应有明确责任和验收条件。行为评测沿用现有 handoff；不靠再加一层编排或更多检查清单来替代缺失的证据。

## 9 月 9 日：TOP 5 修复

| 问题 | 已实现的行为 | 保留的边界 |
|---|---|---|
| 技能包证据绑定 | `skill-package.v3` 绑定完整 `SKILL.md` 及导出资源的内容和路径；修改、增删、重命名都会使旧绑定失效 | 历史证据与成熟度明确沿用，刷新摘要不等于新增行为评测 |
| FIFO 阻塞 | 先以非阻塞方式打开，再检查普通文件类型，及时拒绝 FIFO | 继续拒绝符号链接、特殊文件和校验期间的替换 |
| Intake 恢复 | 当前规范路径的完整 `Write` 候选先校验；损坏或 draft 内容可以恢复；变更后的 approved 内容交给宿主确认 | draft 不能授权代码写入；路径别名不能绕过候选校验；不推导 strict operator pin |
| 产物交接链 | 审查可携带可行动的 blocker 交给作者；小任务复用已批准目标和现有边界；保留或放弃可记录失败验证 | 合入仍需相应审批和通过证据；成功完成与破坏性动作各有授权边界 |
| 入口重复规则 | 合并重复的入口、组合与 priority 说明 | 输入义务、引用规则、范围变化和工作流 gate 仍明确 |

交接检查覆盖三个具体路径：只读审查完成报告但阻止合入；小型 brownfield 修改消费现有边界而不补造架构文档；失败验证产生如实标记未完成的保留记录，同时阻止合入和成功声明。这些是设计推演，不是新的模型实验。

当前静态统计：描述 10,154 字符，入口文本 35,721 字符，Skill 正文 161,165 字符。入口比上一轮减少 2,257 字符，约 5.9%，也比最初审计基线少 999 字符。正文仍比基线长，因为补充了具体判断分支；没有声称整体运行时 token 更省或模型质量更好。

实现边界见[证据绑定规则](../quality/evidence-content-binding.md)、[adapter 说明](2026-07-16-claude-pretooluse-adapter.md)和[评测交接](../../eval/meta/2026-09-08-skill-design-handoff.md)。10 个设计候选继续保持 `review`。

最终实现验证：474 项回归检查、仓库校验、未放宽的上下文预算均通过；46 个源码 Skill 和 40 个公开包通过原生解析，描述最长 303 字符。真实 Claude 宿主确认界面和模型增益尚未验证；本轮未做全局安装或发布。

## 9 月 9 日：下一轮 TOP 5 设计任务

这一轮在执行机制修复后，继续改进 6 个 Skill 的判断与交接，没有新增调度器、产物类型、依赖或评测框架。

| 任务 | 原有问题 | 已实现的设计改进 |
|---|---|---|
| 1. 按依赖处理反馈 | 一个模糊评论阻塞全部修复；同一根因也可能被拆成重复操作 | 对照当前版本归并发现，暂停受影响的组，继续独立且已授权的修复；修复后交回复审，不自称获批 |
| 2. 消费实现输入 | 仅列产物名和 TDD 前置步骤，没有说明复用、缺失决策和续做 | 从已批准范围及当前代码、测试开始；按需要求架构/API 决策，向评审交接实际 diff 与证据边界 |
| 3. 证明重构收益 | 指标下降代替实际收益；既有代码似乎必须先走功能开发 | 比较同一个维护操作改前改后的成本，明确保持的行为，以当前收益解释新增结构 |
| 4. 按风险设计验证 | 固定比例、数量、工具与执行型 gate，阻塞仅需制定策略的工作 | 为真实风险选最低足够层级，保留项目硬性规则，区分计划中的检查与实际运行结果 |
| 5. 区分估算与承诺 | 未知任务仍需填数字；缺容量或负责人时没有诚实的排期路径 | 记录范围或未知，区分主动工作和等待，不编造 Agent 提速；依据不足时只交付暂定计划 |

I/O 契约同步说明下游需要什么：反馈记录保留发现编号和待决问题；功能与重构交接保留版本、验证和未覆盖边界；策略供 CI 与选定的 E2E 工作消费，测试报告只记录真实执行；估算交给有容量依据的计划。工作流允许时可复用已有文档章节。

设计推演覆盖五种情况：独立修复与有争议的 API 评论并存、已有测试的功能续做、改善具体维护操作的重构、只制定策略而不编造运行结果，以及供应商等待时间未知的排期。它们是契约推演，不是模型收益评测。

新增修订的 6 个 Skill 从 `tested` 回到 `review`，历史证据和包身份保留。全库当前为 2 个 production、23 个 tested、21 个 review；两轮共 16 个设计候选待行为复验，公开面仍为 40 个包。

本轮静态统计：描述 9,978 字符，正文 162,641 字符，入口保持 35,721 字符。预算没有放宽。实际验证与后续行为场景见[交接记录](../../eval/meta/2026-09-08-skill-design-handoff.md)。

本轮验证：76 项相关检查、仓库校验、上下文预算和 `git diff --check` 通过；46 个源码 Skill 与 40 个公开包通过原生 Gemini CLI 0.39.1 解析。独立设计审查未发现需修的实质问题。上一批 474 项全量检查属于执行机制修复快照，本轮未重复全套或运行模型评测。

用户已批准按建议完成全库设计验收。本轮沿用已有范围和授权，重点仍是 Skill 设计与组合，行为评测另行交接。英文规范与完整证据见[全库验收记录](../reviews/2026-09-09-skill-design-acceptance.md)。本节是非权威中文说明，不增加规则。

| 范围 | 修正后的行为 |
|---|---|
| 问题澄清、市场、用户研究、可行性 | 接受已有充分输入；允许约束下的单一方向、没有支持证据的市场机会结论、已有研究材料的直接综合和内部项目价值判断 |
